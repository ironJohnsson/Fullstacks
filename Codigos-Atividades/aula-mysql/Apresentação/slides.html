02 / Visão Geral

Aplicação Fullstack com TypeScript & MySQL 8

Isolamento: Por que o Frontend NÃO acessa o Banco?

  • Vazamento de Segredos: Credenciais de banco no código JS do cliente ficam expostas a qualquer usuário via DevTools.
  • Ausência de Validação: Qualquer cliente mal-intencionado poderia forjar requisições destrutivas como DROP TABLE.
  • Esgotamento de Conexões: Centenas de abas abertas simultâneas esgotariam o limite de conexões do MySQL.

Proteção: O Papel Central do Backend Node.js

  • Filtro & Sanitização: Validação de tipos, comprimentos de texto e formatação de e-mails antes de chamar o banco.
  • Mapeamento de Erros: Converte códigos técnicos nativos do MySQL (ex: ER_DUP_ENTRY) em respostas HTTP 409 limpas.
  • Pool Centralizado: Reutiliza até 10 conexões TCP persistentes com controle de fila concorrente.
04 / Modelagem de Dados

Estrutura Relacional no MySQL (DDL)

Definição do esquema relacional com tipos de dados dimensionados e constraints de unicidade.

SQL (banco.sql) MySQL 8.0+ / InnoDB Engine 
-- Criação da base com suporte internacional a 4 bytes por caractere
CREATE DATABASE IF NOT EXISTS aula_mysql
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

USE aula_mysql;

-- Tabela alunos com chave primária auto-incremental e e-mail único
CREATE TABLE IF NOT EXISTS alunos (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT,
  nome VARCHAR(120) NOT NULL,
  email VARCHAR(160) NOT NULL,
  curso VARCHAR(120) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uq_alunos_email (email)
) ENGINE=InnoDB;

Codificação: utf8mb4 vs utf8

O utf8 legado do MySQL aceita apenas 3 bytes. O utf8mb4 suporta 4 bytes, essencial para acentuação da língua portuguesa, caracteres especiais e símbolos internacionais.

Chave: INT UNSIGNED

Elimina números negativos irrelevantes para identificadores e dobra a faixa de IDs possíveis para mais de 4,29 bilhões de registros possíveis.

Restrição: UNIQUE KEY (email)

Cria um índice em B-Tree que impede, no próprio motor físico do SGBD, o cadastro duplicado de um mesmo e-mail, garantindo integridade ACID irrefutável.

05 / Backend & Infraestrutura

Connection Pool: Escalabilidade sem Sobrecarga

Evitando o alto custo do handshake TCP e autenticação SSL a cada requisição HTTP.

Configuração no TypeScript

src/config/database.ts 
import { createPool } from 'mysql2/promise';

export const pool = createPool({
  host: process.env.DB_HOST ?? '127.0.0.1',
  port: Number(process.env.DB_PORT ?? '3306'),
  user: process.env.DB_USER ?? 'root',
  password: process.env.DB_PASSWORD ?? '',
  database: process.env.DB_NAME ?? 'aula_mysql',
  waitForConnections: true,
  connectionLimit: 10,
  queueLimit: 0
});

Vantagens Técnicas do Connection Pool

  • Zero Latência de Handshake: Em conexões isoladas, cada query gasta de 15ms a 80ms para negociar TCP/SSL. Com o pool, a conexão já está aberta e disponível em < 1ms.
  • Reaproveitamento Inteligente: Uma thread requisita uma conexão, executa a query e a devolve automaticamente ao pool para a próxima solicitação.
  • Fila Concorrente (queueLimit: 0): Quando as 10 conexões estão ocupadas, as próximas requisições aguardam ordenadamente na memória em vez de estourar erro de conexão.
  • Fail-Fast Health Check: A função testConnection() executa SELECT 1 no boot antes de subir o servidor HTTP.
06 / Segurança da Informação

Blindagem contra SQL Injection & Validação Defensiva

Como Prepared Statements binários tornam matematicamente impossível alterar o comando SQL original.

Inseguro: Concatenação Direta de Strings

VULNERABILIDADE CRÍTICA 
// Entrada direta no SQL:
const sql = "SELECT * FROM alunos WHERE nome = '" + nome + "'";

// Se o atacante enviar como nome:
// ' OR '1'='1
// A query resultante se torna:
// SELECT * FROM alunos WHERE nome = '' OR '1'='1'
// (Retorna e vaza todos os registros da tabela!)

Protegido: Prepared Statement Binário

IMPLEMENTAÇÃO NO PROJETO 
// Parâmetros vinculados por placeholder (?):
const [resultado] = await pool.execute<ResultSetHeader>(
  'INSERT INTO alunos (nome, email, curso) VALUES (?, ?, ?)',
  [novo.nome, novo.email, novo.curso]
);

// 1. O MySQL compila o plano da query com ?
// 2. Os valores são enviados em pacote separado de dados.
// 3. Qualquer caractere é tratado como DADO PURO.

Validação por Regex

E-mails passam por regex estrita emailValido(email) antes de qualquer chamada ao banco de dados.

Limites de Tamanho de Campo

Validação defensiva de comprimentos (nome <= 120, email <= 160) evitando estouro de payload.

Captura de ER_DUP_ENTRY

Captura o código interno do MySQL e converte para HTTP 409 Conflict com mensagem limpa e amigável.

08 / CRUD em Detalhes

Operação CREATE: Inserção Segura & Unicidade

Fluxo técnico da submissão no cliente até a gravação e retorno da chave primária gerada.

Código da Rota no Backend (src/routes/alunos.ts)

POST /api/alunos
router.post('/alunos', async (req: Request, res: Response) => {
  const { nome, email, curso } = req.body ?? {};

  // 1. Validação de Tipos e Limites
  if (typeof nome !== 'string' || !emailValido(email)) {
    return res.status(400).json({ mensagem: 'Dados inválidos.' });
  }

  try {
    // 2. Execução com Prepared Statement
    const [resultado] = await pool.execute<ResultSetHeader>(
      'INSERT INTO alunos (nome, email, curso) VALUES (?, ?, ?)',
      [nome.trim(), email.trim(), curso.trim()]
    );

    // 3. Retorno com ID gerado pelo MySQL
    res.status(201).json({
      mensagem: 'Aluno cadastrado.',
      aluno: { id: resultado.insertId, nome, email, curso }
    });
  } catch (erro) {
    if (emailDuplicado(erro)) {
      return res.status(409).json({ mensagem: 'Este e-mail já está cadastrado.' });
    }
    res.status(500).json({ mensagem: 'Erro interno ao cadastrar.' });
  }
});

Detalhamento das Camadas do CREATE

  • Validação no Cliente (HTML5 + TS): Atributos required, type="email" e maxlength bloqueiam envios vazios antes de consumir requisições de rede.
  • Validação Estrita no Servidor: A verificação com a função regex /^[^\s@]+@[^\s@]+\.[^\s@]+$/ e length <= 120 garante que clientes que contornem o formulário não insiram lixo no banco.
  • Recuperação de insertId: O MySQL gera a chave primária sequencial via AUTO_INCREMENT. O driver retorna o número através da propriedade resultado.insertId do tipo ResultSetHeader.
  • Status 201 Created vs 409 Conflict: O retorno 201 carrega o objeto completo inserido. Se a constraint UNIQUE KEY uq_alunos_email detectar duplicidade, o backend captura ER_DUP_ENTRY e responde com status 409.
09 / CRUD em Detalhes

Operação READ: Listagem Geral & Filtro Dinâmico LIKE

Como a leitura de dados combina segurança contra injeção e mitigação de concorrência assíncrona.

Código da Rota no Backend (src/routes/alunos.ts)

GET /api/alunos & GET /api/alunos?nome=...
router.get('/alunos', async (req: Request, res: Response) => {
  const nome = typeof req.query.nome === 'string' 
    ? req.query.nome.trim() : '';

  try {
    // Cláusula dinâmica com parâmetro seguro
    const [linhas] = nome
      ? await pool.execute<AlunoRow[]>(
          'SELECT id, nome, email, curso FROM alunos WHERE nome LIKE ? ORDER BY id DESC',
          ['%' + nome + '%']
        )
      : await pool.execute<AlunoRow[]>(
          'SELECT id, nome, email, curso FROM alunos ORDER BY id DESC'
        );

    res.status(200).json({ alunos: linhas });
  } catch (erro) {
    res.status(500).json({ mensagem: 'Falha na consulta.' });
  }
});

Mecanismos de Eficiência e Segurança

  • Binding Seguro de Wildcards: O caractere curinga % é adicionado ao argumento ['%' + nome + '%'] e transmitido como dado, impedindo qualquer injeção dentro da cláusula LIKE.
  • Ordenação Recente Primeiro: A cláusula ORDER BY id DESC exibe os alunos recém-cadastrados imediatamente no topo da tabela.
  • Controle de Race Conditions no Cliente: O frontend incrementa a variável numeroConsulta a cada busca. Se uma resposta de rede demorar e chegar depois de uma busca mais nova, a resposta antiga é descartada com segurança.
  • Manipulação Limpa do DOM: Utilização de corpo.replaceChildren() para recriar as linhas da tabela de forma atômica e eficiente.
10 / CRUD em Detalhes

Operação DELETE & Projeto da Operação UPDATE

Validação numérica de parâmetros de rota, verificação de linhas afetadas e boas práticas de alteração.

Exclusão Implementada (DELETE /api/alunos/:id)

src/routes/alunos.ts
router.delete('/alunos/:id', async (req, res) => {
  const textoId = req.params.id;

  // Validação: apenas inteiros positivos seguros
  if (!/^[1-9]\d*$/.test(textoId)) {
    return res.status(400).json({ mensagem: 'ID inválido.' });
  }
  const id = Number(textoId);

  const [resultado] = await pool.execute<ResultSetHeader>(
    'DELETE FROM alunos WHERE id = ?', [id]
  );

  // Verificação de existência
  if (resultado.affectedRows === 0) {
    return res.status(404).json({ mensagem: 'Aluno não encontrado.' });
  }

  res.status(200).json({ mensagem: 'Aluno excluído.' });
});

Projeto Arquitetural do UPDATE (PUT / PATCH)

Para estender o sistema para edição inline completa na tabela:

PROJETO: PUT /api/alunos/:id
// Rota recomendada para atualização completa
UPDATE alunos 
SET nome = ?, email = ?, curso = ? 
WHERE id = ?;

// Desafios Críticos no UPDATE:
// 1. Se affectedRows === 0: Retornar 404 Not Found.
// 2. Se o novo e-mail já existir em OUTRO aluno:
//    O MySQL dispara ER_DUP_ENTRY -> Retornar 409 Conflict.
// 3. Sanitização idêntica ao CREATE para todos os campos.

Confirmação in-page no DELETE: A interface utiliza um card acessível com botões "Confirmar" e "Cancelar", eliminando os incômodos diálogos bloqueantes de window.confirm().

12 / Interface do Usuário

Frontend Reativo, Prevenção de XSS e Acessibilidade

Interação ágil e segura sem a necessidade de frameworks pesados de terceiros.

Prevenção Contra XSS

O código nunca utiliza innerHTML com dados de alunos. Cria elementos via document.createElement() e atribui com textContent.

Se um aluno se cadastrar como <script>alert(1)</script>, é exibido como texto literal inofensivo.

Controle de Race Conditions

Um contador atômico numeroConsulta garante que respostas lentas de buscas anteriores sejam descartadas se o usuário já digitou um novo filtro.

Garante que o estado visual corresponda exatamente ao texto digitado no campo de busca.

Acessibilidade (A11y)

Mensagens de status utilizam aria-live="polite" e role="status", permitindo que deficientes visuais recebam avisos por leitores de tela.

Confirmação in-page sem usar o intrusivo e inacessível window.confirm().

Ciclo de Interação do Cliente:

  1. Usuário preenche formulário → Disparo de evento submit capturado por formulario.addEventListener.
  2. Feedback visual imediato ("Cadastrando aluno...") com desativação temporária do botão para evitar duplo envio.
  3. Disparo de POST /api/alunos com JSON e cabeçalho Content-Type: application/json.
  4. Tratamento de sucesso (201) → Limpeza dos campos, mensagem de sucesso e inserção na tabela sem recarregar a página.
13 / DevOps & Resiliência

Automação de Ambiente & Script ensure-db.js

Garantindo que o servidor só inicialize quando o banco MySQL estiver operacional.

Funcionamento do ensure-db.js

  • Verificação Socket TCP: Tenta abrir conexão na porta 3306 com timeout de 600ms usando o módulo nativo net.
  • Auto-start de Contingência: Caso a porta esteja fechada, tenta inicializar o serviço MySQL automaticamente via tarefa do Windows ou spawn do mysqld.exe.
  • Polling de Confirmação: Realiza até 20 tentativas com intervalos de 400ms até confirmar que o banco está pronto para conexões.

Scripts Automatizados no package.json

package.json
"scripts": {
  "build:backend": "tsc -p tsconfig.json",
  "build:frontend": "tsc -p tsconfig.frontend.json",
  "build": "npm run build:backend && npm run build:frontend",
  "prestart": "node scripts/ensure-db.js",
  "start": "node dist/server.js",
  "dev": "npm run build && npm start"
}

O hook nativo prestart do npm garante a execução do ensure-db.js automaticamente antes do servidor ligar.
